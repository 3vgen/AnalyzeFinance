# Журнал решений

Архитектурные решения проекта (ADR). Каждая запись: контекст, решение, последствия. Это источник «почему сделано так» для следующего агента.

## Как добавлять решение

Формат: **ADR-NNN. Название** → Контекст, Решение, Последствия, Статус. Новые решения добавляются в конец; изменение решения — новый ADR со ссылкой на старый.

## Принятые решения

### ADR-001. Целевой стек — Python + PostgreSQL + SQLAlchemy

- **Контекст**: сервис анализа личных финансов с веб-интерфейсом; нужна надёжная работа с историческими денежными данными и аналитикой.
- **Решение**: Python 3.12, PostgreSQL, SQLAlchemy 2 (async) + Alembic, Pydantic v2, FastAPI. Аналитика — Polars.
- **Последствия**: единый язык (Python) для API и расчётов; СУБД с транзакциями и миграциями; детали — [[Технологический стек]].
- **Статус**: принято.

### ADR-002. Целевой продукт — API + веб-интерфейс

- **Контекст**: сервис должен быть удобен пользователю, а не только CLI-инструментом.
- **Решение**: сначала REST API (FastAPI), далее веб-интерфейс поверх него.
- **Последствия**: API — главный контракт; UI подключается к API. Детали — [[Архитектура сервиса]].
- **Статус**: принято.

### ADR-003. Мультипользовательская модель

- **Контекст**: сервис предназначен для нескольких независимых пользователей.
- **Решение**: серверное мультипользовательское приложение с изоляцией данных по владельцу (`owner_id`).
- **Последствия**: требуется аутентификация, сквозная проверка доступа, учёт владельца в [[Модель данных|модели данных]] и аналитике. Детали — [[Пользователи и доступ]].
- **Статус**: принято.

### ADR-004. Деньги — Decimal и исходная валюта без пересчёта

- **Контекст**: финансовые данные в нескольких валютах (см. [[Валюты]]).
- **Решение**: суммы хранить как `Decimal` в валюте операции; пересчёт только на этапе отчётов по курсам на дату.
- **Последствия**: нет потери точности и ошибок округления при хранении; пересчёт воспроизводим.
- **Статус**: принято.
