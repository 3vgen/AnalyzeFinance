# Журнал решений

Архитектурные решения проекта (ADR). Каждая запись: контекст, решение, последствия. Это источник «почему сделано так» для следующего агента.

## Как добавлять решение

Формат: **ADR-NNN. Название** → Контекст, Решение, Последствия, Статус. Новые решения добавляются в конец; изменение решения — новый ADR со ссылкой на старый.

## Принятые решения

### ADR-001. Целевой стек — Python + PostgreSQL + SQLAlchemy

- **Контекст**: сервис анализа личных финансов с веб-интерфейсом; нужна надёжная работа с историческими денежными данными и аналитикой.
- **Решение**: Python 3.12, PostgreSQL, SQLAlchemy 2 (async) + Alembic, Pydantic v2, FastAPI. Аналитика — Polars.
- **Последствия**: единый язык (Python) для API и расчётов; СУБД с транзакциями и миграциями; детали — [[Технологический стек]].
- **Статус**: принято.

### ADR-002. Целевой продукт — API + веб-интерфейс

- **Контекст**: сервис должен быть удобен пользователю, а не только CLI-инструментом.
- **Решение**: сначала REST API (FastAPI), далее веб-интерфейс поверх него.
- **Последствия**: API — главный контракт; UI подключается к API. Детали — [[Архитектура сервиса]].
- **Статус**: принято.

### ADR-003. Мультипользовательская модель

- **Контекст**: сервис предназначен для нескольких независимых пользователей.
- **Решение**: серверное мультипользовательское приложение с изоляцией данных по владельцу (`owner_id`).
- **Последствия**: требуется аутентификация, сквозная проверка доступа, учёт владельца в [[Модель данных|модели данных]] и аналитике. Детали — [[Пользователи и доступ]].
- **Статус**: принято.

### ADR-004. Деньги — Decimal и исходная валюта без пересчёта

- **Контекст**: финансовые данные в нескольких валютах (см. [[Валюты]]).
- **Решение**: суммы хранить как `Decimal` в валюте операции; пересчёт только на этапе отчётов по курсам на дату.
- **Последствия**: нет потери точности и ошибок округления при хранении; пересчёт воспроизводим.
- **Статус**: принято.

### ADR-005. Первичные ключи: UUID + естественные ключи для справочников

- **Контекст**: мультипользовательский сервис, данные импортируются из внешних источников.
- **Решение**: бизнес-сущности (пользователи, счета, категории, транзакции) — первичный ключ UUID. Справочные таблицы ([[Валюты]]) используют естественный ключ — код ISO.
- **Последствия**: нет утечки числа записей, удобно для синхронизации и импорта; справочники остаются читаемыми.
- **Статус**: принято.

### ADR-006. Модель данных этапа 1 — ядро

- **Контекст**: нужна минимальная схема для импорта и аналитики (см. [[Статус проекта]]).
- **Решение**: ядро из `users`, `accounts`, `categories` (дерево через `parent_id`), `transactions`, `currencies` + `exchange_rates`. См. [[Модель данных]] и [[Схема базы данных]].
- **Последствия**: категории — дерево (adjacency list); транзакции хранят валюту операции; изоляция через `owner_id`; аудит через `is_archived`; дедупликация импорта через уникальный `external_id`.
- **Статус**: принято.

### ADR-007. Аутентификация — JWT

- **Контекст**: мультипользовательский сервис с API (см. [[Пользователи и доступ]]); нужен метод аутентификации.
- **Решение**: JWT-токены (access; при необходимости refresh), пароли хешируются (bcrypt). Конфиг в `testfinance/core/config.py`.
- **Последствия**: бесшовно для API и будущего веб-интерфейса; требуется безопасное хранение секрета (`JWT_SECRET`) и контроль срока жизни токена.
- **Статус**: принято.

### ADR-008. MVP — только рубли, без конвертации валют

- **Контекст**: сервис рассчитан на обычного пользователя; на старте предполагаются финансы в рублях.
- **Решение**: работаем только с RUB. Мультивалютность и пересчёт по курсам не реализуем (см. [[Валюты]]). Механика хранения суммы с валютой и таблица `currencies`/`exchange_rates` остаются в модели (ADR-004/ADR-006), но на MVP счета и операции заводятся в RUB.
- **Последствия**: проще расчёты и аналитика (не нужен пересчёт); для пользователей с мультивалютными финансами — ограничение, снять позже.
- **Статус**: принято.
